Je veux que tu conçoives et développes une application web front-end personnelle permettant de **suivre, monitorer, analyser et coordonner mon entraînement**.

L'objectif n'est pas simplement de créer un dashboard de statistiques, mais un véritable **cockpit de pilotage de mon entraînement**, qui centralise mes données Garmin et mon programme d'entraînement provenant de Coach Campus afin de m'aider à comprendre ma charge, suivre ma progression et prendre de meilleures décisions au quotidien.

## 1. Contexte

J'ai déjà développé deux serveurs MCP que l'application pourra utiliser :

1. Un MCP Garmin permettant d'accéder à mes données Garmin.
2. Un MCP Coach Campus permettant d'accéder à mon programme / mes entraînements Coach Campus.

Ces MCP existent déjà. **Ne recrée pas leur logique métier et ne simule pas leurs données.**

Commence par inspecter les outils, ressources et schémas exposés par ces MCP afin de comprendre précisément :

* quelles données sont disponibles ;
* quelles opérations sont possibles ;
* quels identifiants sont utilisés ;
* quelles données sont historiques ;
* quelles données sont prévisionnelles ;
* quelles données peuvent être récupérées à la demande ;
* quelles actions peuvent éventuellement être déclenchées.

Si certaines informations nécessaires à l'application ne sont pas disponibles via les MCP, identifie clairement les limitations plutôt que d'inventer des données.

# 2. Vision produit

Je veux une application qui réponde essentiellement à cette question :

> **"Où en suis-je dans mon entraînement, comment ai-je réagi à la charge récente, et que dois-je faire aujourd'hui et dans les prochains jours ?"**

L'application doit donc mettre en relation :

**Planifié → Réalisé → Réaction du corps → Charge → Progression → Prochaines séances**

Elle doit permettre de comparer ce qui était prévu avec ce qui a réellement été réalisé.

L'interface doit être pensée comme celle d'un **coach / athlete performance dashboard**, pas comme une simple application de tracking sportif.

# 10. Intelligence de coordination

Un des objectifs majeurs est de détecter les incohérences ou situations intéressantes dans le planning.

Exemples :

* plusieurs jours de charge élevée consécutifs ;
* séance intense après une mauvaise récupération ;
* séance importante non réalisée ;
* volume beaucoup plus élevé que prévu ;
* séance réalisée beaucoup plus intensément que prévu ;
* accumulation de fatigue ;
* changement important dans la charge ;
* semaine atypique ;
* progression positive ;
* baisse de performance à effort comparable.

Présente cela sous forme de **"Insights"**.

Exemples :

> ⚠️ Charge élevée
> Les 4 derniers jours représentent une charge supérieure à ta moyenne récente.

> ℹ️ Écart au plan
> La séance de mardi a été réalisée à une intensité supérieure à celle prévue.

> ✅ Bonne tendance
> Ton allure moyenne s'améliore à fréquence cardiaque comparable sur les 4 dernières semaines.

Ces insights doivent être basés uniquement sur les données réellement disponibles et sur des règles explicites.

**6. Progressive disclosure.**
Afficher d'abord l'information importante, puis permettre d'aller dans le détail.

**7. Mobile friendly.**

**8. Testable architecture.**

**9. No unnecessary complexity.**

**10. Data transparency.**
L'utilisateur doit toujours pouvoir comprendre d'où vient une information.

# 24. Routine mobilité du matin

Je fais chaque matin une routine de mobilité fixe.

Cette routine ne doit pas être générée ou modifiée automatiquement.

Elle comprend exactement les exercices suivants :

### 1. Claps devant / derrière

Bras tendus.

Effectuer des claps :

* devant le corps ;
* puis derrière le dos.

Durée : **1 minute**

Objectif :

* mobilité des épaules ;
* ouverture de la cage thoracique ;
* mobilité du haut du corps.

### 2. Balancement des bras

Bras tendus.

Un bras monte pendant que l'autre descend, puis inversion.

Durée : **1 minute**

Objectif :

* mobilité des épaules ;
* coordination ;
* ouverture du haut du corps.

### 3. Genoux hauts + ouverture/fermeture des bras

Lever alternativement le genou droit puis gauche le plus haut possible.

Les bras sont ouverts à environ 90°.

Lorsque le genou arrive au point le plus haut :

* les mains viennent toucher le genou devant le corps.

Lorsque le pied repose :

* les bras s'ouvrent ;
* la cage thoracique se déploie.

Alterner droite / gauche.

Durée : **1 minute**

Objectif :

* mobilité de hanche ;
* coordination ;
* mobilité du haut du corps ;
* ouverture de la cage thoracique.

### 4. Rotation du buste

Bras tendus devant le corps.

Effectuer des rotations du buste droite / gauche.

Durée : **1 minute**

Objectif :

* mobilité thoracique ;
* rotation du tronc.

### Règle importante

Cette routine du matin est **fixe**.

L'application doit simplement permettre de :

* l'afficher ;
* la cocher comme réalisée ;
* suivre la régularité ;
* éventuellement visualiser la régularité dans le temps.

Elle ne doit pas modifier automatiquement son contenu.

# 28. Génération de la routine du soir

Chaque soir, l'application doit pouvoir générer une routine de **maximum 8 minutes**.

La sélection des exercices doit tenir compte de :

1. mes faiblesses actuelles ;
2. mes priorités de mobilité ;
3. ma charge de course récente ;
4. ma séance de course récente ;
5. ma séance prévue le lendemain ;
6. mon état de récupération lorsque les données sont disponibles ;
7. les exercices réalisés les jours précédents ;
8. la nécessité de varier les mouvements.

Exemple :

Si ma mobilité de cheville est une priorité et que j'ai une séance de côtes prévue demain :

**Routine du soir**

* mobilité cheville : 2 min
* soléaire : 1 min
* dorsiflexion dynamique : 1 min
* ouverture de hanche : 2 min
* mobilité pied : 2 min

Total : **8 min**

La routine doit rester courte et réaliste.

---

# 29. Principe de progressivité

Ne pas chercher à travailler toutes les faiblesses tous les jours.

L'application doit établir une hiérarchie :

**Priorité 1**
→ faiblesse importante et pertinente pour la course

**Priorité 2**
→ limitation secondaire

**Priorité 3**
→ entretien

La routine quotidienne doit généralement cibler 1 à 3 problématiques maximum.

L'objectif est la **régularité**, pas la complexité.

# 31. Séparation mobilité / récupération / renforcement

Important :

L'application doit distinguer clairement :

**Mobilité**
→ améliorer l'amplitude / qualité du mouvement.

**Activation**
→ préparer un mouvement ou une séance.

**Récupération**
→ favoriser une sensation de récupération après l'entraînement.

**Renforcement**
→ augmenter la capacité musculaire / stabilité.

Si un exercice est en réalité du renforcement, ne pas le présenter comme un simple exercice de mobilité.

À terme, l'application pourra éventuellement proposer du renforcement, mais ce n'est pas le rôle principal de la V1.

# 42. Interaction avec la course

* fessiers ;

* mollets ;

L'application doit simplement **mettre en évidence la situation afin de permettre une décision éclairée**.

# 51. Règle de priorité

La course reste mon **sport principal**.

Cela signifie que lors de l'analyse des conflits potentiels, l'application doit donner une priorité particulière aux séances importantes de course.

Exemple :

Si :

* séance de force jambes importante ;
* puis séance de fractionné le lendemain ;

l'application doit attirer l'attention sur cette succession.

À l'inverse, une séance de vélo facile peut être considérée comme une sollicitation différente et potentiellement compatible avec une séance de course, selon les données disponibles.

Ne pas appliquer de règles rigides sans contexte.

# 54. Principe fondamental

Mon objectif n'est pas de maximiser la quantité d'entraînement.

Mon objectif est de **coordonner intelligemment plusieurs formes d'entraînement afin de progresser principalement en course à pied**.

Le système doit donc toujours raisonner en termes de :

**stimulus → récupération → adaptation → progression**

et non simplement :

**nombre de séances → nombre de kilomètres → statistiques.**
